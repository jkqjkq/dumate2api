本次同步的改动（按影响面排序）：

  upstream-errors.js（新增）—— **千问与 Qoder 共用的上游错误识别**。
    两个产品是同一套 COSY 协议栈，错误形状也一致。判据复制两份必然漂移：
    2026-10-22 修 Qoder 的 `provider_error`（小写字符串 code）时，千问那份
    还是旧的 `/^[A-Z]/` 判据——同类「HTTP 200 + 空回答」在另一条通道上
    继续存在。含 payloadError / envelopeStatus：
      - 数字 code >= 400
      - 字符串 code：纯数字按数字判；其他非空串只要带 message / type 就认
      - `error` 对象**先于** `type` 判（否则 `{type:'error',error:{...}}` 会被
        字符串化成 `[object Object]`，脏串还会写进账号 lastError 显示在界面上）
      - 非信封的裸错误体（上游 4xx/5xx 常见）也在 envelopeStatus 里兜住
      - `code:0` / `code:'success'` 这类成功标记明确不认

  qoder/chat.js —— 三处：
    (1) payloadError / envelopeStatus 改为 require 共享实现；
    (2) **postStream 支持 AbortSignal**：识别到错误帧后立即断流。Qoder 零额度
        时是**挂起**而不是报错，不主动断就要等 socket 空闲超时（600s），
        客户端早已超时；中止时 resolve（带 aborted 标记）而不是 reject，
        避免把调用方手里的 firstErr 盖成无信息的网络错误；
    (3) 单次结算守卫：abort 会同时触发 req 与 res 的 error/end。

  qoder/index.js —— 四处：
    (1) **`[DONE]` 是哨兵、不是上游数据帧**。旧实现把它也算成「已吐帧」，
        于是 `200 + 纯错误体` 的 `!sent` 兜底永远走不到（修复对它要修的场景
        仍然无效），4xx 时 `err.sent` 恒 true → 429 不换号。现在哨兵延后到
        状态检查之后再转发，`sent` 只由真实数据帧置位；
    (2) 识别到错误帧即 `ac.abort()` 上游；
    (3) resolveModelWithFetch 加 **in-flight 去重**（冷缓存 + 并发请求时各拉
        一次模型表 = 各等一次 20s）；
    (4) 删除死代码 warmup()（无调用方，server.js 直接调 warmupModels）。

  qwenwork/chat.js + qwenwork/index.js —— 两处：
    (1) 错误识别改 require 共享实现（补上旧判据漏掉的小写字符串 code 与
        非信封错误体）；
    (2) 流式路径同样修哨兵语义——它复制了同一段逻辑，同样会被 `[DONE]`
        误置 sent。

  server.js —— 三处：
    (1) **翻译器路径的错误埋点**：翻译器在 emit('error') 里**同步**
        finish(502)，外层再传 extra 是 no-op（logRequest 按 _logged 去重）。
        错误改挂到 req 上，让第一次 done 就能带上；翻译器硬编码的 502
        还原成上游真实状态码。实测 `/v1/responses`、`/v1/messages` 的埋点
        从 `{status:502}` 变为 `{status:402, error:"qoder 402: quota exhausted"}`；
    (2) 启动块尊重 `DUMATE_QODER_AUTOSTART=off` / `DUMATE_TRAEWORK_AUTOSTART=off`
        （/v1/models 早就按它跳过，启动块此前没跟：关闭的通道仍会打网络、
        仍报「就绪」）；
    (3) 直连通道的错误统一走 done。
